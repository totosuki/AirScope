# AirScope データベース設計

- 初版作成日: 2026-06-28
- 最終更新日: 2026-06-29
- 対象環境: Azure 開発環境
- 対象実装: `functions/function_app.py`、`functions/airscope_current.py`

## 1. 目的

AirScope が受信した ADS-B テレメトリを Azure Cosmos DB for NoSQL に保存し、次の2つの利用目的を両立する。

1. 受信メッセージの履歴を保持し、ログ表示や後日の集計に利用する。
2. セッション内の機体ごとの最新状態を保持し、Web 地図へ効率よく表示する。

本書は、Git 管理するデータベース設計の正本とする。データ構造、ID、partition key、TTL、indexing policy、更新規則を変更する場合は、実装と同じ変更で本書も更新する。

## 2. データフロー

```text
dump1090-fa またはデモデータ
  -> edge
    -> Azure IoT Hub
      -> built-in endpoint (Event Hubs 互換)
        -> Azure Functions: ProcessAirScopeTelemetry
          -> Cosmos DB account: airscope
            -> database: airscope
              ├─ telemetry
              └─ current_aircraft
```

Azure Functions は1つの入力メッセージに対して、最初に `telemetry` へ履歴 item を保存し、必要な識別情報と位置情報がある場合に `current_aircraft` を更新する。

## 3. 現在の物理構成

2026-06-28 に Azure CLI で確認した開発環境の構成を示す。

| 項目 | 現在値 |
| --- | --- |
| Cosmos DB account | `airscope` |
| API | Azure Cosmos DB for NoSQL |
| Capacity mode | Serverless |
| Default consistency level | Session |
| Multiple write locations | 無効 |
| Database | `airscope` |

### 3.1 コンテナ一覧

| Container | 目的 | Partition key | Default TTL |
| --- | --- | --- | --- |
| `telemetry` | 受信メッセージ履歴 | `/session_id` | 未設定 |
| `current_aircraft` | 機体ごとの最新状態 | `/session_id` | 86,400秒（1日） |

両コンテナとも、partition key kind は `Hash`、unique key は未設定である。

## 4. Partition key 設計

現在は両コンテナで `/session_id` を使用する。

### 4.1 採用理由

- 講義・実験などのセッション単位でデータを取得しやすい。
- Web の初期表示では、対象セッション内の履歴または現在機体をまとめて読む想定である。
- 1セッション内の query に partition key を指定できる。

### 4.2 制約

- 長時間の常時受信では、1つの `session_id` に書き込みが集中する。
- 複数受信局を同一セッションへ集約する場合も、同じ logical partition に集まる。
- 機体単位でセッション横断の履歴を読む query は cross-partition になる。

セッションの長期化、受信局の増加、書き込み量の増加が確認された段階で、`receiver_id`、`icao24`、合成値、階層 partition key などを再評価する。Cosmos DB の partition key は既存コンテナ上で単純変更できないため、変更時は新コンテナへの移行計画を作る。

## 5. `telemetry` コンテナ

### 5.1 役割

IoT Hub から受信した payload を履歴として保存する。edge が送信したデータ構造を維持し、Azure Functions が保存用メタデータを追加する。

### 5.2 ID

```text
<session_id>:<icao24>:<received_at または sent_at>:<uuid>
```

同じ機体・同じ観測時刻のメッセージが複数回処理されても衝突しないよう、末尾に UUID を付ける。

### 5.3 スキーマ

```json
{
  "id": "demo-session:86D9A1:2026-06-28T14:20:00.000Z:<uuid>",
  "schema_version": "airscope.telemetry.demo.v1",
  "source": "airscope-demo",
  "session_id": "demo-session",
  "sent_at": "2026-06-28T14:20:00.000Z",
  "telemetry": {
    "icao24": "86D9A1",
    "callsign": "ANA245",
    "lat": 35.5523,
    "lon": 139.7798,
    "altitude_ft": 12800,
    "ground_speed_kt": 286,
    "track_deg": 72,
    "vertical_rate_fpm": 640,
    "squawk": "3301",
    "seen_at": "2026-06-28T14:20:00.000Z",
    "received_at": "2026-06-28T14:20:00.000Z",
    "receiver_id": "airscope-demo-rpi",
    "distance_km": 18.4
  },
  "ingested_at": "2026-06-28T14:20:01.000Z"
}
```

### 5.4 フィールド

| Path | 型 | 必須性 | 説明 |
| --- | --- | --- | --- |
| `id` | string | 保存時必須 | Cosmos DB item ID。Functions が生成する |
| `schema_version` | string | 推奨 | payload schema の識別子 |
| `source` | string | 推奨 | データ生成元。デモは `airscope-demo` |
| `session_id` | string | 推奨 | partition key。欠損時は raw item 上で `unknown-session` をID生成に使うが、payload自体は補完されない |
| `sent_at` | ISO 8601 string | 推奨 | edge が送信した時刻 |
| `telemetry.icao24` | string | 推奨 | ICAO 24-bit address |
| `telemetry.callsign` | string/null | 任意 | コールサイン |
| `telemetry.lat` | number/null | 任意 | 緯度 |
| `telemetry.lon` | number/null | 任意 | 経度 |
| `telemetry.altitude_ft` | number/null | 任意 | 高度（ft） |
| `telemetry.ground_speed_kt` | number/null | 任意 | 対地速度（kt） |
| `telemetry.track_deg` | number/null | 任意 | 進行方向（degree） |
| `telemetry.vertical_rate_fpm` | number/null | 任意 | 垂直速度（ft/min） |
| `telemetry.squawk` | string/null | 任意 | スコークコード |
| `telemetry.seen_at` | ISO 8601 string | 推奨 | 観測時刻 |
| `telemetry.received_at` | ISO 8601 string | 推奨 | edge が受信・生成した時刻 |
| `telemetry.receiver_id` | string | 推奨 | ADS-B 受信局ID |
| `telemetry.distance_km` | number/null | 任意 | 受信地点からの推定距離（km） |
| `ingested_at` | ISO 8601 string | 保存時必須 | Functions が取り込んだ時刻 |

`session_id` は Cosmos DB の partition key であるため、通常の送信経路では必須として扱う。現在の `build_raw_item` は payload の欠損値をID生成用に代替するだけで、payloadへ `session_id` を追加しない。入力検証の強化時に、この挙動は見直す。

### 5.5 保持期間

現在、container default TTL は未設定である。デモ・実データを送るたびに item とストレージ使用量が増えるため、運用開始前に保持期間を決定する。

初期候補:

- 開発・デモ環境: 7日から30日
- 講義・実験で保存要件がある場合: セッション終了後の分析期間を加味して決定

## 6. `current_aircraft` コンテナ

### 6.1 役割

Web 地図が raw telemetry を毎回集計せずに済むよう、セッション内の各機体の最新状態を保持する。

次のいずれかが欠ける payload は `current_aircraft` の更新対象外とする。

- `session_id`
- `telemetry.icao24`
- `seen_at`、`received_at`、`sent_at` のいずれか
- `telemetry.lat`
- `telemetry.lon`

更新対象外でも、raw item は先に `telemetry` へ保存される。

### 6.2 ID

```text
<session_id>:<icao24>
```

同じセッション・同じ機体は固定 ID へ upsertする。これにより、メッセージ数ではなくユニークな機体数に近い item 数を維持する。

### 6.3 スキーマ

```json
{
  "id": "demo-session:86D9A1",
  "session_id": "demo-session",
  "icao24": "86D9A1",
  "callsign": "ANA245",
  "lat": 35.5523,
  "lon": 139.7798,
  "altitude_ft": 12800,
  "ground_speed_kt": 286,
  "track_deg": 72,
  "vertical_rate_fpm": 640,
  "squawk": "3301",
  "seen_at": "2026-06-28T14:20:00.000Z",
  "received_at": "2026-06-28T14:20:00.000Z",
  "freshness_at": "2026-06-28T14:20:00.000Z",
  "receiver_id": "airscope-demo-rpi",
  "distance_km": 18.4,
  "status": "current",
  "updated_at": "2026-06-28T14:20:01.000Z"
}
```

### 6.4 フィールド

| Field | 型 | 説明 |
| --- | --- | --- |
| `id` | string | `<session_id>:<icao24>` の固定ID |
| `session_id` | string | partition key |
| `icao24` | string | ICAO 24-bit address |
| `callsign` | string/null | コールサイン |
| `lat`, `lon` | number | 最新位置 |
| `altitude_ft` | number/null | 最新高度 |
| `ground_speed_kt` | number/null | 最新対地速度 |
| `track_deg` | number/null | 最新進行方向 |
| `vertical_rate_fpm` | number/null | 最新垂直速度 |
| `squawk` | string/null | 最新スコークコード |
| `seen_at` | ISO 8601 string/null | payload の観測時刻 |
| `received_at` | ISO 8601 string/null | payload の受信時刻 |
| `freshness_at` | ISO 8601 string | 最新性比較に使用する時刻 |
| `receiver_id` | string/null | 受信局ID |
| `distance_km` | number/null | 受信地点からの推定距離 |
| `status` | string | `current`、`stale`、`expired` |
| `updated_at` | ISO 8601 string | Functions が snapshot を保存した時刻 |

### 6.5 更新規則

`freshness_at` は次の優先順で決定する。

1. `telemetry.seen_at`
2. `telemetry.received_at`
3. `sent_at`

既存 item より `freshness_at` が新しい場合だけ upsertする。同じ時刻または古いメッセージでは更新しない。遅延到着した古いテレメトリによって地図上の機体状態が巻き戻ることを防ぐ。

現在の read-compare-upsert は排他的なトランザクションではない。同一機体への高い並行書き込みが発生する段階では、ETagによる楽観的同時実行制御、stored procedure、または別の競合制御方式を検討する。

### 6.6 鮮度状態

保存時点の `now - freshness_at` で判定する。

| 状態 | 既定条件 | Webでの想定 |
| --- | --- | --- |
| `current` | 86,400秒（1日）以内 | 通常表示 |
| `stale` | テスト中は該当期間なし | 薄い表示など |
| `expired` | 86,400秒（1日）超 | 非表示 |

Web表示経路の構築中は、デモデータを確認しやすくするため、`AIRSCOPE_CURRENT_THRESHOLD_SECONDS`と`AIRSCOPE_STALE_THRESHOLD_SECONDS`の既定値をともに86,400秒とする。このため、1日以内は`current`、1日超は`expired`となり、既定では`stale`期間を設けない。一時的な開発設定であり、実機を使ったリアルタイム運用時は30秒と120秒を候補に再調整する。

`status` は item 保存時に計算した値であり、時間経過だけでは自動更新されない。Web API は応答時点でも `freshness_at` を評価し、現在のテスト設定では1日を超えた item を返さない設計とする。

### 6.7 保持期間

container default TTL は86,400秒（1日）である。`current_aircraft` は長期履歴ではなく表示用cacheとして扱い、期限切れ後の自動削除を許容する。

## 7. Indexing policy

両コンテナの現在設定は同じである。

```json
{
  "automatic": true,
  "indexingMode": "consistent",
  "includedPaths": [
    { "path": "/*" }
  ],
  "excludedPaths": [
    { "path": "/\"_etag\"/?" }
  ],
  "compositeIndexes": null
}
```

初期段階では全フィールドを検索可能にし、実際の query pattern が固まった後に RU とstorage使用量を確認して最適化する。

想定する主な query:

- `session_id` で対象セッションを限定する。
- `ingested_at` の降順で最新の raw telemetry を取得する。
- `updated_at` の降順で最新snapshotを取得する。
- `icao24` で特定機体を絞り込む。

複数フィールドの filter と `ORDER BY` を組み合わせるqueryが必要になった場合は、実際のエラーとRUを確認して composite index を追加する。

## 8. 基本 query

### 8.1 セッション内の raw telemetry

```sql
SELECT *
FROM c
WHERE c.session_id = "<session-id>"
```

### 8.2 セッション内の現在機体

```sql
SELECT *
FROM c
WHERE c.session_id = "<session-id>"
```

### 8.3 最新の raw telemetry

```sql
SELECT TOP 20
  c.session_id,
  c.telemetry.icao24,
  c.telemetry.callsign,
  c.telemetry.lat,
  c.telemetry.lon,
  c.ingested_at
FROM c
ORDER BY c.ingested_at DESC
```

### 8.4 最新の current snapshot

```sql
SELECT TOP 20
  c.session_id,
  c.icao24,
  c.callsign,
  c.lat,
  c.lon,
  c.status,
  c.freshness_at,
  c.updated_at
FROM c
ORDER BY c.updated_at DESC
```

### 8.5 Web APIからの読み取り

Web APIはブラウザからCosmos DBへ直接接続せず、Azure FunctionsのHTTP Triggerから次のrouteで読み取る。

| Method | Route | Container | Partition key |
| --- | --- | --- | --- |
| GET | `/api/aircraft/current?session_id=<session-id>` | `current_aircraft` | queryで指定した`session_id` |
| GET | `/api/telemetry/recent?session_id=<session-id>&limit=<n>` | `telemetry` | queryで指定した`session_id` |

`session_id`と`limit`を検証し、Cosmos queryにはparameterを使用する。現在機体APIはresponse生成時に`freshness_at`を再評価し、テスト中は1日を超えたitemを除外する。最新telemetry APIは既定50件、最大200件とし、`ingested_at`の降順で返す。Cosmos DBのsystem propertyはAPI responseへ含めない。

## 9. 整合性とエラー処理

- Cosmos DB account の既定 consistency level は `Session` である。
- raw telemetry 保存に失敗した場合、Function invocation は失敗し、current snapshot処理へ進まない。
- current snapshot保存に失敗した場合も、Function invocation は失敗する。ただしraw itemは既に保存済みの可能性がある。
- Event Hubs trigger の再試行により同じ入力が再処理されると、現在の raw ID はUUIDを含むため `telemetry` に重複相当のitemが増える可能性がある。
- `current_aircraft` は固定IDかつ鮮度比較を行うため、同じ入力の再処理ではsnapshotの巻き戻りを防止できる。

厳密な重複排除が必要になった場合は、IoT Hub message ID、受信局ID、観測時刻などからdeterministicなraw IDを生成する設計を検討する。

## 10. セキュリティ

- Cosmos DB endpointとkeyはFunction AppのApp Settingsに保存し、Git管理ファイルへ実値を記載しない。
- 現在はCosmos DB key認証を使用する。本番に近づける段階ではmanaged identityとRBACへの移行を検討する。
- `receiver_id` に住所、氏名などの個人情報を使用しない。
- ADS-Bは公開ブロードキャストだが、不要な長期保持を避け、個人追跡を目的としない。

## 11. 変更・移行方針

次の変更はデータ互換性に影響するため、本書、実装、テスト、Azure設定を同じ作業で更新する。

- partition key
- container名
- ID形式
- schema version
- TTL
- freshness判定
- indexing policy
- consistency level

partition keyやID形式を変更する場合は、原則として新containerを作成し、必要に応じて既存データを移行してからApp Settingsのcontainer名を切り替える。
